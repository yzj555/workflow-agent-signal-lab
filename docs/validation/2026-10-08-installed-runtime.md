## 30 分钟测试与结论边界

两个正式 run 的根 Agent 持续接收本地流式响应，安装包自己的计时器累计有效时间；同一浏览器页以两个客户端频率读取两个根的只读快照。每次核对完整 RPC 信封、请求 ID、应用层 `ok` 与根身份，不只检查 HTTP 200。两根最终各记录一次模型请求、零命令，活动额度各为 1,800,000 ms；预留与未知时长均为零，最终 Host 根／角色／模型占位均为零。

该场景 HTTP 读取 p50 约 3.8 ms、p95 约 6.8 ms、最大约 592.3 ms；测试 Host 采样 RSS 峰值约 556 MiB，事件循环 p95 约 31.9 ms。没有将最大延迟隐藏，也没有据此承诺全部请求低于 150 ms。

这是两个客户端频率的实际 HTTP 读取，**不是两个独立页面的完整渲染测试**。负载是小历史数据和脚本化流，不等于外部模型、重型工程、满容量 Journal 与 4 个长期角色同时施压。期间同机还运行了上述短时 L1 验证，因此任何延迟／内存数字只作该场景观察，不作为安静机器基准、端到端 SLO 或 OS 内存配额。

## 失败证据保留

- 旧临时 Host 缺少部分依赖，未当作插件回归或静默修补；重新建立了固定官方组件的独立 Host，并保存新的 frozen lock。不能声称新旧第三方传递依赖逐项相同。
- 开发夹具先后修正预设 setup 返回值、原生标题辅助请求分类、首次界面声明等待和工作区会话绑定。它们不计入成功样本，也没有修改生产包来适应夹具。
- `smoke-v7` 的原回执只检查 HTTP 200，漏掉了无效 RPC 信封，**不作为负载验收证据**。对应 `duration-v1` 被主动停止，仅终止自有隔离 Host，原失败现场保留；没有完成长跑或正常关闭证明。修正后的短测为 `smoke-v8`，长测为 `duration-v2`。
- `engineering-v1` 中普通 `node --test` 的子进程创建因 Windows 受限令牌返回 `spawn EPERM`；插件拒绝了与真实退出码不符的 PASS。脚本化模型却重复提交错误报告，触发测试自身请求保险；失败及收尾前快照不一致保留，不改成绿色样本。
- `engineering-v2` 因夹具遗漏 `sandboxPolicy` 注入在正式运行建立前退出。正确声明依赖后的 `engineering-v3` 通过。没有为避开上述失败自动切换 Full access。
