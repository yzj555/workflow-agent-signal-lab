# 文件容量守卫修正与候选核验

日期：2026-09-20。结论：**本批缺口已修复，隔离候选验证通过，尚未部署。** 这是 V1-03／Gate C 的一个子项，不代表完整资源策略或 Production v1 已完成。

## 发现与修正

旧构建的四项回归均失败，失败回执单独保留：

| 问题 | 修正 |
| --- | --- |
| 超过 16 MiB 的 UTF-8 写入仍能进入原生文件工具 | 调用前按实际 UTF-8 字节数拒绝；中文字符数不能替代字节数 |
| 小参数的 `replace_all` 可膨胀成超大文件 | 根据当前文件、实际匹配次数和换行处理检查输出大小；先判定长度，再创建有界结果，不先构造超大替换结果 |
| 第 101 个文件被拒绝前已创建备份对象 | 文件数量、外部变化和总量核对移到保存备份之前 |
| 原始检查点超过 64 MiB 时已创建多余备份 | 恰好 64 MiB 可用；再多一个字节即在备份和原生写入前拒绝 |

另外把检查点、文本对象和工作区文件读取改为有界读取：即使文件在 stat 后增长，也最多读取上限外的一个字节，随后关闭句柄并报错；不会截断、覆盖或自动修复用户文件。

这些检查只收紧既有容量边界，不替代官方文件工具、观察版本校验或沙箱策略。编辑的 UTF-8 解码、BOM、CRLF 检测、非重叠字面替换及换行恢复按已固定的 DSH `0.1.5-rc.1` 实际实现核对，并直接与官方 `LocalFileSystem` 输出作测试对照；上游变化后须重验。

## 验证结果

- 新增 13 项：10 项控制器／真实文件提供者容量验证、3 项对象存储和读取中增长验证。
- 四项旧版失败 → 修复后全部通过；包含“刚好 16 MiB”“100 个文件”“刚好 64 MiB”正边界，不靠降低额度或跳过大文件转绿。
- 还覆盖 Unicode、多处删除、字面 `$&`、CRLF/BOM、孤立 CR 及换行恢复导致的超限；原始文件、快照和备份目录在拒绝时保持预期。
- 空输出目录构建成功，双端类型检查通过；同一候选连续两轮全量 **391/391**，均无失败、取消或跳过。原 Gate B 恢复用例包含在两轮全量中。
- 52 个源码、50 个测试及夹具、24 个构建输出已冻结。候选拥有独立依赖链接，`@local/workflow-agent-signal-lab` 指向候选自身，避免误测正在服务的旧模块。新增的官方文件提供者仅用于开发测试，未替换线上提供者。
- 新旧读取器对同一份 20 条历史记录的快照和所有 run 状态完全一致；没有 Journal 协议变化或数据迁移。
- 线上 20 条记录、部署构建、writer、配置和预设保持不变；没有重启、真实模型任务、授权门禁或预算配置变化。

复现：按 [开发说明](../../README.md#开发与验证) 在独立目录重新链接匹配 DSH 开发依赖后构建，再运行 `node --test tests/workflow-project-controller.test.mjs tests/workflow-artifact-limits.test.mjs` 和全量 `npm test`。不要在运行中的服务目录重建。

## 未完成与限制

- 容量是单文件 16 MiB、单次实现检查点最多 100 个文件／64 MiB 原始内容；**不等于整个历史数据目录的总磁盘配额或保留策略**。已保存的历史和备份不自动删除。
- 前置检查约束当前捕获版本及此次参数，不承诺阻止外部进程在检查后另行修改文件；后置摘要／有界读取仍会检测不一致，不能据此声称 OS 隔离。
- 本批没有发布或加载到 3080；当前在线实例仍为此前通过恢复矩阵的构建。完成其余 Gate C 项后再申请具体激活范围。
