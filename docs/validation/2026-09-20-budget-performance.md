日期：2026-09-20。状态：**离线记账候选完成短时及 30 分钟持续验证，未激活；Gate C 未通过。** 后续 Host 准入是另一份候选，不能将本批测量自动外推到它的完整请求链路。

## 修正内容

大历史下，原路径每次累计时长或请求／命令记账都会重新验证和回放全部事件。本次将“纯记账更新”与“包含业务事件的提交”分开：

- 仅复用本模块已经完整校验、克隆且深度冻结的记录对象。身份依据是私有 WeakMap 中的精确对象，不是 Session ID、revision、摘要或调用者自行冻结的对象。
- 纯记账仍完整检查 JSON、预算 schema、历史 run 引用、结束／请求修订号一致性；容量依据规范化 UTF-8 字节增量精确更新。
- 业务事件变更仍做完整回放；超限、冲突、持久化故障、原子结束和未知退出的处理不变。没有新增持久化格式或放宽预算。
- 冷打开重新完整验证；测试使用 JSON 往返破坏对象身份后独立回放对照，不能用同一缓存证明缓存正确。

资源配置现有一个明确标记为未激活的 [候选与说明](../operations/workflow-resource-policy.md)。240 次模型准入／40 次命令／30 分钟有效时长等数值来自现有机制，尚不是经真实任务分布校准后的最佳策略。本次被测的 450 项基线不包含后续 [Host 并发准入](../design/workflow-host-admission-v1.md)。

## 短时测量

环境：Windows x64、Node 26.1.0、16 个逻辑 CPU、约 31.8 GiB 内存；官方 DSH `0.1.5-rc.1`，源码提交 `183f08e9c6dde7e36cd2318eaee70b0da08fb35e`。每项实际运行 60 秒，2 个合成根会话，每根 8500 事件；普通行约 3.1 MiB，较大行各 13 MiB。每项 236 个读取样本、14 个显式记账／追加样本。回执保留未取整数据。

同负载的两次优化后观察均低于优化前；这支持避免重复回放有实际收益，但不能从单机短样本承诺固定提升比例。每根 13 MiB 时最大事件循环延迟约 **277 ms**，并非所有延迟都小于 150 ms；仍不能承诺重负载下页面绝无卡顿。

原生参照使用官方 JSONL 的完整事件读取／追加；工作流使用有完整语义校验的 SQLite 行及投影快照。二者数据布局、返回体和写入语义不同，不能据快照读取时间声称“整个插件比原生快”。原生 A 的早期阶段曾并行运行约 250 ms 的配置单测，因此补了无该测试干扰的 B。性能项与全量回归串行执行，没有同时跑大测试集。

优化后 A/B 的首次冷开约 279／220 ms；13 MiB 场景约 342 ms，最后冷开约 378 ms。三个优化后短时场景均在关闭并重新打开存储后得到完全相同的快照、预算和事件 revision，无故障、无伪造 PASS/FAIL。计时器自己的周期结算包含在总 CPU／事件循环观测中，不逐项列入 14 个显式写入延迟样本。
