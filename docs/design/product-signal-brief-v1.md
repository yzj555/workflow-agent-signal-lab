# Product Signal Brief v1

> 冻结日期：2026-09-07  
> 状态：`SUPERSEDED BEFORE OBSERVATION / PREFLIGHT ONLY`  
> 证据范围：`personal-utility / builder-as-judge`  
> 目标裁决：`proceed / revise / stop`

## 1. 治理声明

本检查验证的唯一问题是：**在 DSH 原生输入继续作为主要交互的前提下，只读 Workflow View 是否能让用户更快判断“现在、下一步、是否需要我”，并改善一次具体决策。**

该 Brief 在工程样机已经存在之后才冻结，因此是对后续投入的前瞻检查，不能倒签为架构 v0.16 要求的“0A 前 Product Signal Gate”，也不计入 H1—H3 的 Operational Product Gate 样本。此前讨论、原型认可与真实文本 PASS 均不预填本轮分数。

三个场景均使用官方 DSH 页面、原生会话外壳与原生 composer；工作流状态采用显著标记 `SIMULATION / 非真实运行` 的确定性只读回放。回放不得创建正式 Run、调用模型、提交批准、执行系统动作或写入工作流 Journal。Chat-only 对照与 Workflow View 必须表达同一事实，不能故意弱化对照组。

冻结后不得依据用户反应修改场景、标准答案或门槛。若发现渲染错误或事实不一致，该场景标记 `INVALID / infrastructure`，修复后以新版本 Brief 重开，不按失败或通过计算。

## 2. 固定观察流程

每个场景按以下顺序执行：

1. 在原生对话中展示用户最初表达，以及 Agent 已公开的必要回应；不另造聊天框。
2. 按场景预定顺序分别查看 Chat-only 和 Workflow View。顺序固定为：S1 Chat-first、S2 Workflow-first、S3 Chat-first。
3. Workflow 投影稳定后立即开始五秒观察，请用户回答：**现在在做什么？下一步是什么？现在是否需要我？**
4. 原样记录回答、耗时及是否三项全部语义正确。不得提示答案或在计时中解释界面。
5. 查看对照后询问：Workflow View 是否改善了一次具体判断？是否愿意在相似任务中使用？记录 `yes / no` 与用户原话理由。
6. 记录仅因状态表达不清产生的额外轮次；正常需求澄清、对照评价和用户主动改目标不计入。

单场景通过必须同时满足：五秒内三项全部正确；`avoidableTurn = 0`；用户能够指出一个被改善的具体判断并愿意在相似任务中试用。整轮至少 `2/3` 场景通过，且没有把普通讨论误呈现为已启动任务，才可输出 `proceed`。

## 3. 冻结场景

### S1 · 需求仍含糊

- 用户原始表达：`帮我整理一份本周研发风险简报，供周会使用。`
- 已知事实：用途是周会；尚未明确读者、信息来源、统计时间边界和输出长度。
- 投影状态：尚未建立正式 Run；处于需求澄清，等待用户补充关键范围。
- 标准答案：
  - `now`：正在澄清简报范围，尚未开始生成。
  - `nextStep`：用户补充读者、来源、时间边界和长度后，Agent 合并需求供确认。
  - `attention`：需要用户回答关键问题。
- 反证重点：阶段条让用户误以为任务已经启动，或无法辨认缺少哪些输入。

### S2 · 验证失败后返回

- 用户原始表达：`起草一份内部测试环境维护通知；必须写明维护时间、影响范围和恢复说明，完成后独立验收。`
- 已知事实：初稿已有维护时间和影响范围，但缺少恢复说明；独立 QA 判定必选项失败，已返回同一实现角色进行一次范围内修正。
- 投影状态：当前是实现返工，不是继续验证，也不是整轮失败；无需用户介入，除非修正需要扩大已确认范围。
- 标准答案：
- `now`：返工已进入实现阶段，日志记录内容 Agent 已重新派发；这不是实时心跳声明。
  - `nextStep`：修正版完成后，由独立 QA 重新逐条验收。
  - `attention`：当前不需要用户操作。
- 反证重点：用户把 QA 失败理解成整轮结束，或不知道下一步会重新验收。

### S3 · 讨论后决定不执行

- 用户原始表达：`评估是否把每日状态报告改为自动外发；没有明确收件人授权就不要执行。`
- 已知事实：讨论发现缺少收件人范围与外发授权；用户选择本次不执行。
- 投影状态：分析已结束，没有建立执行 Run，没有产生外发动作，也没有待处理门禁。
- 标准答案：
  - `now`：本次评估已经结束，并决定不执行。
  - `nextStep`：没有自动下一步；以后取得范围和授权时可在原生输入中重新提出。
  - `attention`：当前不需要用户操作。
- 反证重点：把“不执行”画成失败、等待批准或仍在后台推进。

## 4. 固定记录字段

每个场景必须保存：`scenarioId`、展示顺序、开始时间、稳定投影摘要、标准答案、用户原始回答、`elapsedMs`、三项逐项判定、`avoidableTurns`、Chat-only 对照摘要、具体判断改善答案、相似任务使用意愿、场景裁决和理由。

整轮另存：错误／写请求审计、有效场景数、通过数、失败模式、`decision` 与理由。`proceed` 仅表示值得继续支付下一小步工程成本；不代表 Runtime、安全、恢复、H1—H3 或市场价值已经通过。

## 5. 停止规则

- 任一只读场景产生正式 Run、副作用、模型调用或用户批准：立即 `stop`，该结果不能被其他场景抵消。
- 至少两个有效场景通过且无误呈现：`proceed`。
- 有效场景达到三个但不足两个通过：`revise`；必须根据共同失败原因修改交互假设，再冻结 v2。
- 因基础设施问题不足三个有效场景：保持 `NOT_STARTED / INCOMPLETE`，不得给出产品裁决。

## 6. 观察前预检记录

首次夹具预检发现空状态响应含一个未声明测试字段，严格客户端按设计显示为读取失败；同时第三方文件栏占用了主内容宽度。此时尚未向用户提出观察问题、未启动计时，也没有采集或查看用户反应。测试夹具已在正式观察前移除非法字段，并仅通过文件栏自己的折叠按钮收起该栏；场景事实、标准答案、顺序与门槛未改变，因此不形成场景裁决或版本后见修改。

第二次夹具预检发现最初借用的 UI 外壳属于一条已有两个子 Agent 的已完成会话，导致 `availability=absent` 时仍显示与场景无关的原生 Agent 观察。正式观察改用已存在且没有子 Agent 历史的空白 Workflow 会话，仅在浏览器响应中注入同一只读场景。没有创建、改写或删除原生会话；场景定义和评分口径仍未改变。

第三次预检改为在浏览器响应中排除外壳会话的历史子 Agent，三个场景的只读性与渲染均通过。但 S1—S3 的预检截图已产生并可能出现在协作工具输出中，不能再当作未见过的五秒观察刺激。因此 v1 不采集用户分数、不输出产品裁决；正式观察使用事实类型和门槛不变、具体内容全新的 v2。

该空白会话随后被确认遵守 DSH 的原生侧栏隐藏规则，不能成为用户可选择的回放入口。夹具因此继续使用可见外壳，但在临时浏览器的 `session.list` 响应中排除其历史子 Agent 行，并新增空态零 Agent 断言；真实 `session.list` 与会话历史保持不变。这仍属于观察前基础设施校验，不产生用户样本。
