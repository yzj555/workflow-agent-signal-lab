## 用户入口

主要交互仍在 DSH 原生输入框，没有新增聊天窗口。

| 当前状态 | 用户可以做什么 | 不会发生什么 |
| --- | --- | --- |
| 请求或时长预算耗尽 | 原生对话核对状态、申请补额或结束 | 不继续实现、测试、派发或自动重试 |
| 核对对话额度也耗尽 | `/workflow-budget` 查看；`topup`／`end` 发起原生确认 | 原生命令不调用模型、不直接批准 |
| 已批准补额 | 查看“等待继续”；用下一条原生消息表达意图 | 用量不清零，后台通知不恢复执行 |
| 角色已中断且已确认回收 | 原生确认结束本轮，再重新确认新任务 | 不用补额复活旧角色或沿用旧 lease |
| 停止仍未知 | 保留阻塞，走原有逐项核实／人工处置路径 | 不写成 CANCELLED、PASS 或已证明停止 |
| 已明确结束 | 有界交接到新草案，或新开原生会话 | 新任务不继承原批准，历史不删除 |

无模型命令的精确用法：

```text
/workflow-budget
/workflow-budget topup
/workflow-budget end
```

命令不接收自定义数额或执行指令；`topup` 固定提出 +60 次模型请求、+10 次命令的申请；已有时长账户另提出 +10 分钟有效时长。要提出其他有界数额，可在原生对话表达，由 `workflow_budget` 整理，最终以原生确认卡中的精确数额为准。没有预算账户的历史运行只返回说明；只有请求账户的旧 Run 不添加时钟。

## Alpha 限额（不是费用保证）

- 初始执行上限仍由 Host 冻结，默认模型 240、命令 40；本片未更改活动配置。
- 每次补额最高 +120 模型、+20 命令、+30 分钟有效时长，必须增加当前耗尽的资源；每 Run 最多三次批准。累计硬界限为 100,000 模型请求／10,000 命令／24 小时有效时长。时长字段仅适用于已有计时账户，可以申请仅增加时长。
- 核对池初始 12 次模型请求，每次批准补额增加 12 次，累计使用不清零；每条新用户 turn 最多 3 次。
- 原生确认结束后另外最多 3 次模型请求用于交接新草案，保证在核对池耗尽后仍有有限交接通道；再次用尽时提示新开原生会话。每条新用户 turn 仍至多 3 次。最多三次补额时，控制与交接总量最多 51 次。
- 自动插件通知、引发耗尽的旧 turn、重启自动恢复均不能消费核对池。新 turn 必须在原生 `user/message` 事件中出现 `source.kind=user`。
- 人工等待不产生模型准入，不扣请求次数。第三片对时长另做等待／后台工作观测；核对对话本身不计执行时长，仍受有界核对池和根响应监管约束，不宣称具有整轮费用或绝对墙钟保证。

这些数额是待校准的 Alpha 防失控策略，不是生产性能或费用结论。一个请求可能很长；模型辅助标题、压缩及 provider 内部额外请求仍不在本账户内。

## 原生确认及安全边界

预算工具和命令都通过官方 `userQuestions.ask` 取得答案。卡片显示当前用量、追加值与新总上限、申请原因、保留项以及“不自动推进／不扩权／不恢复旧 Agent”的限制。Host 只接受对应 question id 的单一精确批准标签；旧 id、多选混合、拒绝、取消与回答到达时版本变化都不补额。

在请求前和回答落盘前分别检查精确根 Agent、当前 Run、领域 revision、当前 Host lease 和 Journal 退出事实。存在任何活动、回收中或未知范围时拒绝处置。`topup` 还拒绝已有终态或任何中断角色；`end` 可以在确认回收后结束，保持中断原因和验收证据。已有人工结束 ABANDONED 的预算关闭不改写它的 unknown 或终态。

批准补额只修改资源上限，持久化 `awaitingResume=true`；工具结束当前 turn，不自动通知或派发。刷新／冷打开保留暂停。新的原生用户消息才会解除这层暂停，随后正常请求仍按执行额度预记账，合同、权限和需求门禁仍需满足。**这里只验证新的用户消息来源，不声称 Host 能证明这句话的语义就是“继续”；Agent 应按该消息意图回答或推进。**

## 持久化与恢复

`budgets.accounts[].recovery` 保存初始上限、封闭次数、控制消耗、恢复次数、等待恢复标记、申请与决定历史、结束标记。它与旧 `used`、当前 `limits` 同处一个原子 KV 行。

- 每个请求冻结唯一 id、领域 revision、封闭轮次、原上限、追加值、时间和原因。原生批准／拒绝另记 `decisionAudit`；`operator=unverified` 不证明谁亲手点击。
- 冷读校验有效上限等于初始上限加已批准追加、计数与预算 revision 一致、请求顺序与轮次一致、结束预算必须对应工作流终态。
- 结束未完成的 Run 时，决定记录、未完成任务取消和 CANCELLED 一起提交；持久化失败不发布部分成功。
- 新 Host 把未决预算请求记为 cancelled，不从历史答案续接；批准过的上限、累计用量及等待新用户消息状态保留。
- 第一片没有 recovery 字段的账户读时不变，第一次真实写入时补齐恢复元数据；完全没有账户的历史记录不迁移。
- 领域 revision 与预算 revision 独立；核对模型请求不会让正在等待的原生确认过期。领域状态变化仍使旧确认失效。
- 仍有 16 MiB 单行、10,000 领域事件、每账户 128 条预算处置请求上限，不截断历史。旧严格读取器不认识新字段；在线启用后不可只降级 JS 而宣称数据可回退。
