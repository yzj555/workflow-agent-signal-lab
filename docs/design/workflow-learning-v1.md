# 工作流沉淀与复用 v1

状态：2026-09-08 已实现事件、控制器、原生裁决、确定性检索、显式覆盖、停用和只读投影；2026-09-10 补齐终态证据 ID 出口、决定来源审计、候选文本预检及跨键重叠拦截；2026-09-11 将退回修改改为候选级持久状态，并通过原生输入框承载具体修订意见。当前整体类型检查、构建及 140 项回归通过。本文只描述 `workflow-text-pilot/1` 与 `workflow-project-pilot/1` 的有界能力。

## 1. 产品原则

沉淀是交付后的第七阶段，不是新的任务表单：

1. Agent 先从本轮已保存证据中整理最多三条候选；没有价值时直接记录“本轮无候选”，不询问用户。
2. 有候选时只出现一个 DSH 原生问题流程，每条候选占一页并做一次单选：“当前项目”“同类工作流”“内容有误，退回修改”或“不采纳”。问题同时确认规则内容与生效范围；小标题显示经验类型和证据数，弱引用层完整展示规则，并仅在语义边界处断行。卡片不使用含义模糊的箭头缩写，完整证据仍留在只读工作流记录中。每条决定独立持久化：某条被退回不会撤销或重问其他候选。Agent 随后在原生输入框等待用户说明具体改法，只提交该候选的新陈述与修订原因，并只重新确认这一条；不要求重跑实现与验证。
3. 只读工作流页显示候选、依据、作用域和状态，不承担第二套输入或确认。
4. 采纳项不会直接执行，也不会写进全局提示词；它只可能在下一次匹配任务的需求草案中成为可见约束或假设，再经过正常 Signal Gate。
5. 当前用户指令始终更高。协调 Agent 可在 `workflow_propose.learningOverrides` 中说明本轮覆盖原因；覆盖本身和原规则均留痕。

## 2. 候选合同

`workflow_learn` 只在运行已有 `outcome`、没有运行态 Agent、且本轮尚未整理沉淀时可用。每条候选由模型提交以下受限语义，身份和版本由 Host 填入。规则陈述必须是不超过 160 字、不换行且能独立读懂的一段完整可执行规则；证据说明由 Host 根据证据 ID 生成，不能塞入规则正文：

- 稳定 `ruleKey`；
- 一句规则陈述；
- 动作类型：沟通偏好、规划提示或质量约束；
- 风险：低或影响后续执行约束；
- 触发：同作用域始终，或全部精确词项同时命中；
- 建议作用域：当前项目或同类工作流；
- 一到十二个本轮 `EvidenceRecord` ID。协调者必须从终态 `workflow_advance.learningSources` 或 `workflow_status.learning.sources` 逐字取得，不能猜测其他对象的 ID。

Host 拒绝不存在的证据、超过三条的候选和文本工作流中的项目作用域。规则正文还会经过确定性预检：禁止换行、控制／不可见／非法代理字符、未闭合成对符号、缺失句末标点、已知机械误输入，以及当前协议无法证明的操作者身份断言。语义是否正确仍由原生裁决负责，Host 不用模型充当自己的拼写裁判。

进入原生裁决前，Host 会检查本批候选以及适用范围有交集的活动规则。相同动作类型下，同键、规范化后同文，或触发范围相交且达到保守高置信阈值的语义重叠都会被拒绝；因此不能只换 `ruleKey` 绕过。项目候选对比同项目规则与 preset 规则，preset 候选对比同 profile 下所有项目和 preset 规则。命中时返回现有规则 ID、作用域、关系类型及可证明的共同技术词，要求保留、收窄，或先经原生门禁停用旧规则；Host 不自动合并或覆盖用户已经采纳的规则。

Host 根据证据生成 `basis` 与 SHA-256 来源摘要，绑定当前执行 profile；工程规则还绑定规范化工作区身份。模型不能提交 actor、用户身份、项目身份、版本或权限字段。

若用户退回某一候选，首次裁决会立即保存其他候选的采纳／不采纳结果，并把该候选记为 `revision-required`。用户在原生输入框说明改法后，协调 Agent 再次调用同一个 `workflow_learn`，但输入只包含当前 `expectedRevision`、Host 返回的 `candidateId`、修订后的 `statement` 与对用户意见的 `reason` 摘要。Host 固定沿用原候选的证据、规则键、动作类型、风险、触发条件、profile 和项目身份，重新执行活动规则重叠检查，写入一次 `learning/revised`，再为这一条打开原生裁决。已采纳或未采纳的 candidateId 不能通过修订入口覆盖。

## 3. 事件与生效条件

```text
outcome/declared
      │
      ├─ items=[] ───────────────► learning/proposed（本轮无候选）
      └─ 有候选 ─► 文本／重叠预检 ─► 原生分页单选
                                      │
                                      └─ learning/proposed
                                         + learning/decided
                                           ├─ 采纳／不采纳（立即成为最终决定）
                                           └─ revision-required
                                                │
原生输入框说明改法 ─► workflow_learn（单条）──────┘
                         │
                         └─ learning/revised（前文／后文／原因／次数）
                            └─ 只重开这一条原生裁决
                               ├─ 采纳／不采纳（最终决定）
                               └─ 再次退回（继续同一候选，不影响其他项）

下一运行 workflow_propose
      └─ learning/applied（含 applied / overridden）

用户要求停用
      └─ 一次原生确认 ───────────► learning/revoked
```

- `learning/proposed` 只能由协调者在终态后写入，且每个 run 仅一次；来源证据摘要在冷重放时重新计算。
- 首个 `learning/decided` 必须是原生问题回答对应的 user-authority actor，并把全部候选划分为采纳、不采纳或待修订；后续 `learning/decided` 只能覆盖已经写入新版本且等待再次确认的 candidateId。每次决定都必须携带与 actor 关联 ID 一致的 `decisionAudit`。
- `learning/revised` 只能由当前协调者追加到处于 `revision-required` 的候选，且必须匹配上一版正文、使用单调递增的修订次数并实际改变陈述。事件保留修订前后正文和原因；写入后仅该候选进入再次确认状态。
- `learning/applied` 只能由 Host 在新运行终态前写入；即使没有命中也记录空应用集，以清除草案改版前的旧匹配。
- `learning/revoked` 必须是原生问题回答对应的 user-authority actor。停用是追加事件，不删除候选、采纳或既往应用。

这里的 `actor.kind=user` 表示 Host 已通过 DSH 原生用户权限门禁取得回答，不是对物理操作者身份的认证。当前官方 `AskUserQuestionAnswer` 只有问题 ID、选择值和可选自定义文本，不区分用户亲手点击与经用户授权的客户端／代理提交；新决定记录 `decisionAudit={authority:user, channel:native-question, operator:unverified, requestId:<Host 关联 ID>}`。审计和交付文案不得声称“用户亲手操作”或“没有模型代理”。模型仅在对话中转述同意依然不构成该 actor。

旧版只有 `id/statement/basis/proposedScope` 的候选仍可冷读，但因缺少 profile、项目身份、版本和来源摘要，不进入 v1 活动规则检索。

## 4. 确定性准入、检索与冲突

候选准入和运行时检索是两条不同路径。候选准入使用保守、确定性的高置信重叠信号，仅用于阻止明显重复进入新的用户裁决；它比较相同动作类型、相交触发范围、规范化文本、字符二元组相似度以及共享技术词。它不是通用语义搜索，可能漏掉改写幅度大的重复，也可能要求 Agent 对高度相似但确有差异的规则先明确收窄。

运行时复用不做语义相似度推测，检索顺序固定为：

1. 执行 profile 必须完全相同；
2. 项目规则必须命中同一 Host 计算的项目身份；preset 规则只命中同类工作流；
3. `always` 直接命中，`exact` 要求规范化后的草案同时包含全部词项；
4. 同一个 `actionKind + ruleKey` 上，项目规则优先于 preset 规则；
5. 同一精度出现多个活动规则时抛出 `RULE_CONFLICT`，停止自动复用，绝不静默择一。

命中规则按 ID、版本、来源 run、触发原因和本轮状态写入 `learning/applied`。质量规则加入 Requirement 的约束，沟通偏好和规划提示加入假设，均带 `【已确认历史规则 …】` 前缀，因而会在需求确认中直接可见。

## 5. 权限不变量

沉淀不能：

- 授予或扩大工具、沙箱、写入范围、网络、进程或发布权限；
- 删除 Signal、Action、Product、Review、Delivery 或撤销门禁；
- 修改合同冻结命令、任务 DAG、角色身份、验收者或 Host 证据；
- 把用户未选择的候选、模型自述或自然语言“同意”变成活动规则；
- 让其他项目继承项目规则。

规则文本只是待确认 Requirement 的附加约束/假设。所有真正执行仍由现有任务包、角色工具矩阵、最终守卫、证据账本和用户门禁控制。

## 6. 已知边界

- 规则保存在现有按根 Session 聚合的 Journal 事件中，检索需要重放当前插件库；尚未分表、索引、归档或做正式规模性能准入。
- 不支持全局作用域、运行时语义检索、自动合并冲突、已生效规则的原位编辑或跨 profile 迁移。当前运行中尚未最终决定的候选可逐条修订；已采纳规则仍须先停用，再以有新证据支持的新候选提交。
- 用户只能在当前已结束运行中停用当前项目／profile 可见的活动规则；没有独立规则管理页。
- 新 run 创建后，旧 run 不能再追加候选；协调 Agent 应在交付后立即完成沉淀阶段。
- 沉淀质量仍依赖 Agent 是否从证据中提炼出恰当候选；当前验证证明控制边界与可追溯性，不证明真实模型候选质量。
- 当前原生回答协议不提供操作者来源证明；若未来必须区分亲手点击与授权代理，需要 DSH 核心提供受信来源元数据，不能由插件自行推断。

## 7. 实现位置

- `src/workflow-learning.ts`：严格输入、机械文本预检、候选高置信重叠检查、活动规则重建、作用域过滤、精确匹配、版本和冲突关闭。
- `src/workflow-events.ts`：五类沉淀事件、候选级决定合并、修订历史、冷重放和来源摘要核验。
- `src/host/workflow-controller.ts`：候选编制、逐项原生裁决、原生会话修订桥接、规则注入、显式覆盖和停用。
- `src/workflow-run-projection.ts`、`src/client/workflow-stage-display.ts`、`src/client/workflow-surface.ts`：只读阶段与明细。
- `tests/workflow-learning.test.mjs`：采纳、候选级退回与单项复核、修订前后／原因／次数回放、文本预检、跨键重叠、无候选、复用、覆盖、跨项目隔离、冲突、停用、来源审计和事件不变量。
