## 1. 已接通的链路

```text
Host 内部 Journal.commit（未来由受信 Controller 调用）
  → 当前 revision 比较 + 全批事件重放校验
  → 官方 storageDomain / SQLite 单行原子写入
  → 已提交的完整只读 Snapshot
  → 官方 Connection /workflow-runtime/snapshot
  → 原生对话的状态条、顶部入口和只读侧面板
```

原生输入中的需求分析、补问、确认与暂停意图还没有连到上述内部写入口。没有暴露浏览器写端点、模型控制工具或自然语言自动分类器；安装本层不会自动创建业务 Run。

## 2. 状态归属与提交边界

| 项目 | 当前实现 |
|---|---|
| 数据目录 | `F:/dsh/workflow-agent-signal-lab/.dsh/workflow-runtime`，可由 Host 插件 `dataDirectory` 配置 |
| 后端 | 私有 Cordis Context 组合官方 SQLite + storageDomain；不覆盖主 Host 的存储路由 |
| 文件 | `journal.sqlite`（WAL 模式）及 `writer.lock`；运行中可能有 SQLite WAL/SHM 辅助文件 |
| 原子单位 | 根 Session ID 对应一行：schemaVersion、rootSessionId、revision、完整领域事件序列 |
| 序号 | 插件负责连续 `seq`、不倒退的 `time`；revision 为总事件数，与原生 Session seq 无关 |
| 并发 | 同一根 Session 串行；提交必须携带 expectedRevision，不符即拒绝，不静默覆盖 |
| 批次 | 所有事件先一起重放校验；末尾一个事件非法则整批不写入 |
| 可见性 | 等待后端写入成功后才发布 Snapshot；观察者异常不撤销已提交事实、不破坏其他观察者 |
| 故障 | 写入失败或结果不确定后全局停止读写；必须关闭、重新打开并重放核验，不能自动重试授权 |
| 冷恢复 | 读取时校验 schema、根 ID、连续 seq、全部版本与状态迁移；未知版本或坏记录拒绝，不清空重建 |

每个根 Session 同时最多一个未结束 Run；结束后显式创建下一 Run。历史 Run 保留，但新 Run 开始后不能再追加旧 Run。大日志、截图与构建产物保持外部引用，不装进事件正文。

v1 有意使用有界聚合行，避免假设官方具备跨表事务：每个根 Session 上限为 **10,000 个事件 / 16 MiB**，任一超限都拒绝，不截断历史。每次写入会重放和重写聚合行；这不是无限扩展的事件数据库，分段、归档及迁移尚未实现，也没有取得性能准入数据。

## 3. 单写者与恢复

启动时先规范化数据目录，通过 `writer.lock` 的 `wx` 独占创建取得目录所有权，写入随机 instanceId、PID 和开始时间并同步，然后才打开数据库。两个进程争用相同目录时只能有一个成功。

正常关闭顺序为：停止接收提交 → 等待已接收提交结束 → 关闭领域与私有 Context → 校验文件身份和原内容 → 释放自己的标记。标记被替换、损坏或留下未知所有者时，不替别人删除。

异常退出后的遗留标记**不会自动抢占**。需要人工核实原 Host 已完全退出、没有其他写入者，并对停止写入后的整个数据目录做一致备份，再显式隔离遗留标记并重新打开验证。PID 不存在或超时本身不构成自动接管授权；本次没有提供恢复按钮或执行任何锁清理。

这是单机单写者的启动排他，不是多机分布式锁、租约心跳或多用户访问控制；外部程序绕过插件直接修改数据库不在保证范围内。

## 4. 只读投影与连接

- Host 注册官方 `/workflow-runtime` 通道，仅实现 `snapshot`；浏览器使用现有 Connection，不另开服务器。
- 请求为 `{ schemaVersion: 1, rootSessionId }`。请求与响应使用同一份严格 Zod schema，拒绝未知字段、错误版本和跨根 Session 响应。
- Snapshot 只包含目标摘要、阶段、风险、门禁及其失效状态、任务/依赖、Agent 分工记录、验收计数、沉淀计数和历史概要。不包含完整任务包、源码、写入范围、凭据或内部推理。
- 回环信任栅栏拒绝跨站 Origin、`sec-fetch-site: cross-site` 和伪造 Host。它是官方的可达性保护，不是用户登录认证。
- 同一根 Session 的多个组件共用一个进行中请求。有运行时约 2 秒一次；空记录/错误约 5 秒；单次 8 秒超时。没有订阅者就停止，卸载会释放请求和订阅。
- Host connection generation 变化时立即取消旧请求并清空旧展示；迟到响应不能覆盖新状态，revision 倒退被拒绝。失败不继续展示上一轮的批准状态。
- 当前是完整 Snapshot 短轮询，不是正式架构中的长轮询、切片增量更新或自定义推送。浏览器端不自行折叠事件、解释聊天文本或批准门禁。

## 5. 生命周期与诚实展示

| 场景 | 行为 |
|---|---|
| 旧会话 / 新根 ID 没有 Journal | 显示“尚未建立运行”，只读请求不创建记录，不从旧聊天迁移批准 |
| 插件缺席 / Host 断线 / 后端故障 | 显示状态不可用，不解释为空任务或已经停止；未来 Controller 必须同样拒绝推进 |
| 原生 fork / 复制 | 新根 ID 不继承批准；显式工作流分支与迁移尚未实现 |
| 原生会话删除 | 不自动删除 Journal；暂时保留孤立记录，没有自动 GC |
| 原生会话导出 | 不自动携带插件 Journal；插件导出与导入尚未实现 |
| 已持久化的 Agent running | 显示“运行记录”，重启后的进程存活、续接资格和外部副作用核对尚未接入 |
| 旧原生会话中的子 Agent | 可作单独标注的原生观察，不作为新 Journal 的授权或验收事实 |

“继续使用原生输入框”指交互载体保持不变，不代表本切片已经拦截全部旧工具。旧实验预设和 PM 守卫仍是旧行为；在受控入口接管前，不把现有 Crew 调用宣称为受 Journal 强制约束。

## 6. 可复现验证

```powershell
Set-Location F:\dsh\workflow-agent-signal-lab
npm run typecheck
npm run build
npm test
```

当前 **51/51** 通过：既有守卫/协议/策略 20 项，Journal 14 项，官方后端与 HTTP 集成 10 项，客户端状态层 7 项。关键证据包含：

- 另起 Node 进程，恢复同一数据库，得到完全相同的已提交 Snapshot。
- 两个真实进程同时争用一个目录，仅一个取得所有权。
- 额外 SQLite 连接持有写锁，制造真实写入失败；不发布新状态，恢复后仍是上次已提交版本。
- 修改临时测试库为未知 schema，冷打开拒绝且不重置原数据。
- 官方 Host Connection + 官方 Client caller 经真实 HTTP 往返；写 endpoint、跨站和伪造 Host 均被拒绝。
- 取消、超时、连接换代、迟到响应、倒退 revision、无记录及组件共享请求等边界。

重复回归曾暴露测试脚本向已拒绝启动的子进程发送关闭消息的 IPC 收尾竞态；已改为只关闭成功取得所有权的进程，并复用同一个清理 Promise。修正后双进程争用单项连续 15 轮通过，随后完整 51 项回归和真实 Web 检查再次通过。真实插件数据库的根记录数仍为 0，证明本次 UI 查询没有创建业务工作流。

## 7. 下一步与未声明能力

下一步是受信 Controller：核验预设/Session/用户事件来源，生成和确认版本化合同，再以受控 dispatch/continue/report 执行、验证及返回。Journal 的内部 actor 字段本身不是身份认证，不能直接把模型提交的 `actor: user` 当用户许可。

本层不声明完整任务调度、QA 工具隔离、崩溃后 Agent 自动续跑、撤销外部副作用、正式性能预算、多用户安全或跨 DSH 版本兼容。仍需逐项以实现和测试证明。
