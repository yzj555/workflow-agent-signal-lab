日期：2026-09-03。对应代码协议标记：`workflow-text-pilot/1`。

## 1. 当前结论

代码与自动化运行链路已实现；**2026-09-03 在官方 3080 完成一轮真实文本交付**，原生问答门禁批准、内容生成与独立验收均有记录。随后完成提示词／工具隔离修正与阶段标识补全，当前共 94 项离线测试通过；隔离修正于 18:35 经用户授权重启部署，阶段只读投影于 19:14 在确认空闲后重载。启动、历史完整性与真实页面只读检查通过，没有重复调用真实模型。分阶段事实见第 7 节，不把部署检查或脚本化模型测试当成真实用户试用。目标 DSH 版本的回答协议不证明物理操作者身份；此处“门禁批准”只指原生用户权限通道已有结构化回答。

实现范围是“确认需求 → 内容 Agent → 独立验收 → 一次范围内返工 → 重新验收／交付”。这是一条低风险文本闭环，用来验证实际约束，不是整个工作流架构已经交付。

交互仍由原生 DSH 输入框与原生问答组件承担。没有新增聊天窗口，没有浏览器写 RPC，也没有替旧会话补写确认记录。

## 2. 主体与权限

| 主体 | 可以做什么 | 不能做什么 |
|---|---|---|
| 协调 Agent | 澄清、提交版本化需求、发起原生用户权限门禁、推进已批准步骤、停止 | 自称用户批准、直接写项目文件、Shell、网络、进程操作、原始 Crew 委派 |
| 内容 Agent | 读取自己的合同包，提交一个文本交付物 | 批准门禁、提交验收结论、访问项目文件、追加子 Agent |
| 独立验收 Agent | 读取合同和当前交付文本，逐条报告观察及 PASS/FAIL | 读取父对话、实现者对话／自评、工作区源码，改写交付文本，自行豁免标准 |
| 用户 | 在原生问答中批准当前完整合同，或补充和修改 | 无需学习工具参数或在插件面板重复输入 |

预设不再继承 Standard/Crew 的工具集合。根 Agent 绑定必须同时满足：当前官方 registry 的同一个对象、runtime root、无子 Agent 来源／正数委派深度标记、已组合本预设、由本预设生命周期监听器登记。官方 continuable 子 Agent 的运行时所有者并不是其持久父会话，因而也可能出现在 `roots()` 中；不能只用该列表判定协调权限。

原生空白会话切换预设会保留同一个 Agent；插件通过官方 `agent-preset/selected` 事件，在切入时绑定、切出时清理本实例的限制与展示。已有对话的预设固定规则仍由 DSH 执行，没有开放运行中换模式。

子 Agent 使用官方无父历史继承的 `spawn` continuable 路径。在 unpublished setup 中安装具体实例的工具限制和最终拒绝守卫；同时使用完整隔离系统提示词及 runtime-context 抑制。修正后的最终模型输入只呈现 `workflow_packet` 和 `workflow_report`。

`tools.restrict()` 只过滤继承工具，不隐藏随后在子作用域注册的原生 `report`。因此使用官方 `system-prompt/assemble` 的精确 Agent 作用域投影过滤最终工具 schema；它是展示约束，独立的单调执行守卫才是拒绝越权的边界。根提示仅移除已核实的 `crew:pm` 与 `crew:jobs` 两个贡献名，不按正文搜索删除，也不替换根 Agent 的完整提示词；原生身份、用户指令、安全及审批上下文保持原样。

这是同一可信 Host 内的工具和上下文隔离，不是 OS 沙箱。其他恶意 Host 插件或本机高权限程序不在本版威胁模型内。

## 3. 原生确认

1. 用户先在原生对话表达目标；不明确的点继续补问。
2. `workflow_propose` 保存合并目标、范围、排除项、约束、假设、未解决问题、硬性验收标准。
3. 存在未解决问题时，控制层拒绝发起确认。
4. `workflow_confirm` 先持久化版本绑定的门禁，再调用官方 `ctx.userQuestions.ask`。
5. 只接受真实问答服务返回的、本门禁唯一问题的明确批准选项。模型没有 `actor`、`confirmed`、root Session ID 等输入字段。
6. 自由输入“同意，但还需要改……”不会打开门禁；返回原生对话合并新版本。需求改版、取消、异常和过期回答均不能沿用旧批准。

运行时可将未完成的问题标为取消，但不能借系统 actor 批准或拒绝一个用户门禁。日志中的用户 actor 由原生问题 ID 派生，不接受模型转述。

## 4. 派发、验收和返回

正常路径：

`原生确认 → 持久化授权 → 内容 Agent → 文本落盘 → 独立验收 → 全部通过 → 交付`

失败路径：

`独立验收失败 → 保存观察证据 → 原内容 Session 冷恢复返工 → 新交付版本 → 原验收 Session 冷恢复复验`

- 派发 ID、角色、任务包版本先进入 Journal；持久化失败不调用原生派发服务。
- 执行报告必须来自当前分配的真实子 Agent 对象和任务版本，不能通过填写 role 冒充其他角色。
- 文本只写入插件自有 `text-artifacts/<SHA256>.txt`；路径由 Host 构造，不接收模型文件名。内容不可变，读取校验摘要，报告大小有上限。
- 内容完成仅是 implementation 信息，不产生验收通过。
- QA 必须逐条覆盖当前标准，无遗漏、重复或 WAIVED。验收包和证据绑定当前交付版本。
- 成功保存角色报告后，用官方 `ToolRunContext.concludeTurn()` 结束该角色本轮；仍需等待官方 `subagent/end` 才记录正常结束。
- 普通最终文本或无报告的正常退出都不能变成验收通过。
- 原生结束通知可能早于插件持久化；控制层在保存结束状态后再发一条有明确插件来源的通知，防止父 Agent 等待已消耗的通知边沿。
- 返工额度在原生确认里明确为一次。返回时仅采用 QA 的失败证据，不接受模型另加隐含需求；复用两个子 Session ID，保持角色与上下文域不变。
- 任务包改版将关联验收结论转为待验证；旧结果和证据保留在事件历史中。不能用旧 PASS 接受新产物。
- 第二次失败暂停。用户请求停止时只停止本运行持有的子 Agent，不删除历史或产物；不会伪称已经撤销外部副作用。

新 Host 不能把持久化的 running 记录直接视为当前执行凭据。缺少本次派发凭据时报告 recoveryRequired 并拒绝自动继续。

## 5. 实际文件

- `src/host/workflow-engine.ts`：Journal 与 Controller 的生命周期所有者，先撤销／排空控制层，再关闭 Journal。
- `src/host/workflow-control.ts`：官方 questions、Agent registry、continuable 子 Agent、上下文隔离与原生通知适配。
- `src/host/workflow-agent-scope.ts`：区分运行时根节点与持久委派来源，拒绝子角色取得协调权限。
- `src/host/workflow-model-view.ts`：精确作用域的最终提示词／工具展示，保留独立执行守卫。
- `src/host/workflow-controller.ts`：身份、版本、门禁、派发、验收、返工和停止。
- `src/workflow-pilot-contract.ts`：严格输入结构、固定权限边界和合同生成。
- `src/host/workflow-tools.ts`：原生工具入口；浏览器仍只有只读 snapshot RPC。
- `src/host/workflow-artifacts.ts`：插件内不可变文本存储。
- `preset/workflow-agent-signal-lab`：新版受控预设的源文件。

Host 引擎单独构建为自包含入口，避免旧进程加载新入口时复用已经缓存的旧 Journal 内部模块。这不等于承诺已支持任意热更新或跨版本迁移。

原生链路测试实际加载官方 Loader、AgentPresets、AgentLoop、ToolRuntime、JSONL persistence、Subagent runtime、spawn provider、原生 `report` 组件和本插件引擎。模型响应是脚本化适配器，用户问答 provider 也是测试替身，**自动测试没有调用付费模型，也不能用它证明真实用户理解或真实模型判断质量**。Crew 冲突测试使用与已安装 v0.10.0 相同贡献名的夹具，不是对完整 Crew 插件的兼容性认证。

已测到的关键事实：

- 官方预设只暴露允许的工具；后续宽松中间件和实例内新工具都不能绕过最终守卫。
- 协调者的实际模型请求不含 Crew 冲突段，保留测试安全／审批段；其他模式保留自己的提示和工具。空白会话两次切入／切出本预设后，同一个 Agent 正常绑定／清理，另一根会话不受影响。
- 原生 `report` 在控制器之前或之后注册时，子角色最终模型请求仍只有两个工具；手工构造参数正确的 `report` 调用也被角色守卫拒绝，不是因为参数错误而偶然失败。
- 在真实原生循环中完成一次失败与返工：2 个稳定子 Session ID、4 个不同 Activation、4 次正常结束，最终收到第 2 版文本的完整验收。
- 子 Agent 的真实模型请求不包含测试注入的父对话、Host 私有系统段或动态上下文，且工具只有两个。
- 真实运行中的子 Agent 可被停止；协调者和其他根会话不被一并销毁。
- 用户回答歧义、旧版本回答、重复提交、写盘失败、派发失败、错误角色、缺失报告、重复／缺失验收、磁盘产物损坏均不能产生虚假通过。

独立上下文降低了实现者自测偏差，但不是认知独立性或质量的数学保证。程序黑盒测试、工程实现和更复杂风险级别仍须单独接入和验证。
