# 已有数据的离线重配置、升级和代码回退

更新：2026-10-08。当前维护基线为 Windows、固定 DSH `0.2.0-rc.2`／RC.11 与 RC.12、明确停用官方 HMR 的独立 Profile；实际编号升级、失败恢复及保留当前数据的兼容回退已有隔离证据。这不是任意版本升级器，也不是 Production v1 批准。独立生产 Profile 尚未创建；首次空目录配置仍用[首次配置流程](workflow-profile-activation.md)。旧 DSH `0.1.5-rc.1`／RC.5 的显式 startup 验收保留原范围，不外推新版或跨 SDK 回退。

本流程只做三件事：保存当前检查点、用目标版本核对当前数据、生成新的启用配置。它**不停止服务、不安装包、不启动 Host、不恢复旧数据库、不删除 writer 锁，也不批准任务**。

新版差异：RC.11／RC.12 在 DSH 0.2.0-rc.2 已完成实际安装、同版本维护、编号升级、准入失败恢复、保留新增数据的兼容代码回退和卸载重装，见 [新版维护验收](../validation/2026-10-08-dsh-020-maintenance.md)。新版必须显式停用官方 HMR，离线作用域使用公开解析服务，不使用旧 startup 字段或 filesystem fallback；策略影响整个 Profile。下文维护协议的结构也用于新版，但具体载荷和共享组件必须对应精确基线；不能混用旧 SDK 包，也不能恢复旧库补过验收。

## 先区分四类数据

插件代码、工作流私有目录、DSH 原生会话、项目文件是四个不同对象。`capture` 备份工作流目录和已核对的旧包载荷，不是整个 Host 的备份；原生会话、Profile 配置和工作区须另行保护。检查点可能含任务文本、配置和本机路径，只保存在私有位置。

代码可以回退，当前记录不随之倒退。升级后新增的记录必须继续存在；旧检查点发现数据已变化时，只能拒绝，不能拿旧库覆盖新库。

## 前提与停机边界

1. 核对需要操作的精确 DSH_HOME、Profile、Host、私有目录和发布包摘要；保存当前有效 `activation-plan.json`。
2. 获得本次维护授权，确认整个 Host 没有活动任务，按正式退出流程停止，核实身份和退出。不能在运行中的 Profile 安装或移除包。
3. 工具通过与运行时相同的原子 writer 协议排除工作流写者；**这不证明整个 Host 空闲**。已有、过期、损坏或来源不明的 writer 都拒绝，不自动回收。
4. 保留完整的匹配版本 CLI／组件集合、原配置和目标归档。包内 `transitionProtocol: 1` 是目标版本的必要条件；早期 RC.2 可作为升级来源，但不支持自动回退为该版本。

下面均为命令结构，尖括号须替换为已核对的绝对路径；输出子目录必须是新目录，不能覆盖配置、数据或检查点。入口取自验证过的安装包，不使用在线开发目录的旧 `lib`。

## 升级

**先捕获，再离线安装，再验证目标。**

```text
node <已验证工具包>/scripts/transition-workflow.mjs capture
  --plan <当前有效activation-plan.json>
  --output <新的私有升级前检查点目录>
```

捕获时校验配置和载荷，持有 writer，复制工作流数据并回放完整历史状态。SQLite 只在临时副本上打开；原数据库及旁文件不会被回放修改。检查点保存旧载荷摘要、原配置身份和当时的数据，不代表许可已升级。

随后按[官方安装路径](release-build.md)离线安装目标 `.tgz`，核对共享 Host 模块。再用已安装目标包执行：

```text
node <目标安装包>/scripts/transition-workflow.mjs prepare
  --checkpoint <上述目录/checkpoint.json>
  --mode upgrade
  --output <新的升级启用方案目录>
```

工具要求版本方向正确、原 Profile 及其他插件配置未变、资源策略未变、当前数据仍等于检查点；目标解析器不能悄悄丢字段，完整快照及所有 run 状态必须与来源一致。通过只表示可以按既有授权安排启动，不代表任务获批。

启动使用相同 DSH_HOME、实际 CLI 和有序原有 overlays，最后添加新生成的 `workflow-enable.patch.yml`。启动 guard 再核对当前数据，并将**同一个 writer**交给存储；中间不先解锁再抢锁。首次写入的 `transition-accepted.json` 只证明兼容检查通过。后续重启允许合法新数据，但每次仍重新回放，不能凭旧回执跳过检查。

## 同版本重新配置

例如增加一个自定义 preset root：先用旧有效方案捕获，再在停机状态下审阅和修改原配置，保留无关字段。未经明确复核，配置变化会被拒绝。

```text
node <当前安装包>/scripts/transition-workflow.mjs prepare
  --checkpoint <变更前检查点/checkpoint.json>
  --mode reconfigure
  --accept-config-change
  --output <新的重配置方案目录>
```

`--accept-config-change` 仅用于**同版本**的已审阅配置变化，不是跳过检查开关；不能用于升级／回退，也不能改变资源策略或恢复数据。旧启用层失效后，不要直接改它的摘要来绕过 guard。

## 失败后的兼容代码回退

需要两份含义不同的检查点：

| 检查点 | 用途 | 不可用来做什么 |
| --- | --- | --- |
| 最新当前数据检查点 | 证明回退目标可以读取现在的全部记录，包括升级后新增记录 | 不能用升级前的旧数据代替 |
| 已归档目标检查点 | 证明将安装的旧版本就是此前核验的精确载荷 | 不能把其中的旧数据库恢复到当前目录 |

仍须先确认停止。使用当前有效方案捕获最新数据；若配置或载荷损坏，导致有效方案无法核对，应保留现场并进入人工兼容核查。**不能伪造新检查点、改摘要或清空数据让命令通过。**已有检查点只有在当前数据完全未变化时才可继续作为当前数据依据。

保留新版验证工具，在离线安装精确归档目标后执行：

```text
node <已验证工具包>/scripts/transition-workflow.mjs prepare
  --checkpoint <最新当前数据检查点/checkpoint.json>
  --mode rollback
  --rollback-checkpoint <归档目标检查点/checkpoint.json>
  --output <新的回退启用方案目录>
```

工具核对目标载荷、同一 home／Profile／数据目录及当前完整回放。目标不认识的新协议、配置变化或数据变化均拒绝。只有通过后才可按维护授权启动；禁止自动降级解析器或恢复旧库。

## 停用与验收范围

确认空闲并正常退出后，去掉最终启用 overlay 可停用插件；保留数据、配置、检查点和原生历史，不要通过删库停用。是否能继续运行旧会话，另受其预设和工具可用性影响；“历史能看”不是“旧授权能续跑”。

本批已在独立官方 Web 验证升级、同版本重配置、受控启动拒绝、保留升级后新增记录的回退以及停用后打开合成原生历史，见[验收记录](../validation/2026-09-20-profile-transition.md)。RC.6 是同源代码、仅版本不同的演练包，不是新功能版。

尚不覆盖：正式 1.0.0 版本方向、任意 schema 迁移、旧 v0／descriptor v2 原生历史修复、跨 DSH 版本升级、活动 Host 热卸载、资源策略变更或独立用户真实模型任务。当前工具只接受编号 RC；这些限制不能通过人工改版本号绕开。
